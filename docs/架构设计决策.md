# 架构设计决策

> 记录关键设计决策的上下文、备选方案、选型理由和后续可优化方向。
> 目的是让新加入的开发者（和未来的自己）理解"为什么这么设计"而不是"做了什么"。

---

## 1. 图编排：LangGraph vs LangChain Agent vs 自实现状态机

### 上下文

需要编排一个包含 LLM 推理、多工具调用、安全检测、人工审核的客服流程。流程不是线性的一问一答，而是有循环（ReAct）、有条件分支、有中断恢复。

### 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| **LangGraph** | 显式节点 + 边、中断原生支持、checkpoint 自动管理 | 学习曲线、依赖版本演进快 |
| LangChain Agent | 开箱即用、代码少 | 控制流黑盒、HIL 难实现、调试困难 |
| 自实现状态机 | 完全可控、无外部依赖 | 需要自己实现 checkpoint、中断恢复、并发控制 |

### 决策

**选 LangGraph。** 核心原因是 Human-in-loop 的 `interrupt()` 机制——这是 LangGraph 区别于其他编排框架的关键特性。自实现状态机 + 中断恢复的复杂度远超直接引入一个成熟框架。

### 后续

LangGraph 版本迭代快（0.x 阶段），升级时需关注 `interrupt()` / `Command()` API 的兼容性。当前锁定 `langgraph>=0.2.0,<0.5.0`。

## 2. 双路由 vs 单路由：为什么 tool_exec 完成后回 reasoning 而不是 generate

### 上下文

参考 LangGraph 官方 ReAct 模式，tool_exec 之后要么继续 reasoning（ReAct 循环），要么转人工。但为什么不直接去 generate？

### 决策

```
tool_exec → reasoning（继续工具调用）
         → human_handoff（转人工）
```

因为 LLM 在一次推理中可能发起多个工具调用请求，或者调用完一个工具后发现还需要更多信息。直接跳到 generate 会切断 LLM 的"思考-行动"循环。回 reasoning 让 LLM 有机会看工具返回结果然后决定下一步。

### 边界条件

如果 tool_exec 检测到无限循环（同一工具重复调用 3 次），会设 `interrupt_info` 强制转人工，防止 LLM 陷入死循环。

## 3. 安全检测：detector 节点不做 interrupt，静默替换

### 上下文

需要在 LLM 生成回复后做安全兜底。有两种方案：中断让审核员处理，或静默替换。

### 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| **静默替换**（当前方案） | 不阻塞用户、不消耗审核人力 | 用户可能收到词不达意的回复 |
| interrupt 转人工 | 安全性更高，审核员逐条判断 | 审核开销大、延迟高、噪声多 |

### 决策

**静默替换。** 原因：敏感词命中绝大多数是误触（用户说脏话、谐音梗），不需要人工判断。工具调用失败也不需要人工——替换为道歉文案 + 询问是否转人工即可。只有 LLM **主动要求**转人工时，才走完整 interrupt 链路。

### 数据流

```
generate → detector（固定边，不可跳过）
            │
            ├─ 安全通过 → 原始回复
            ├─ 敏感词命中 → 替换为违规警告文案
            └─ 工具失败 → 替换为道歉 + 转人工询问
            │
            ▼
          finish
```

## 4. 双层人工介入 vs 单层

### 上下文

系统需要人工介入能力，有两种触发方式：LLM 主动请求，或系统被动检测。是否需要两层？

### 决策

**双层设计：**

1. **主动升等（业务层）**：LLM 调用 `request_human_escalation` 工具。适用于 LLM 明确知道处理不了的情况（投诉、封禁申诉、超出工具范围）。**触发中断。**
2. **被动兜底（安全层）**：detector 节点检测到敏感词或工具失败。**不触发中断，静默替换。**

这两层职责正交，互不替代。只做主动升等的话，LLM 可能在敏感话题上过度自信直接回复；只做被动兜底的话，LLM 明明知道处理不了却没有途径主动请求帮助。

## 5. 持久化：双存储引擎分离

### 上下文

项目有两种持久化需求：Agent 执行状态（checkpointer）和业务数据（pending_store），两者的访问模式不一样。

### 决策

| 存储 | 用途 | 引擎 | 选择理由 |
|---|---|---|---|
| **Redis** | Agent checkpoint（图执行状态） | `langgraph-checkpoint-redis` (RedisSaver) | 纯内存低延迟、支持 checkpoint 索引、TTL 自动清理 |
| **Redis** | 待审核任务队列 | `redis.asyncio` | 24h TTL 防堆积、async 不阻塞事件循环、降级到内存 dict |
| **SQLite** | 工单 CRUD | `sqlite3` 内建 | 数据量小（千级）、事务简单、零运维 |

为什么不用单一数据库统一所有存储？

- MongoDB/PostgreSQL 对 checkpoint 存储过于重量级（LangGraph 写 checkpoint 非常频繁）
- SQLite 写性能不满足 checkpoint 的高频写入场景（尤其是多线程）
- Redis 不适合存工单（需要复杂查询、关联、聚合）

### 后续

工单量增长后可将 SQLite 迁移到 PostgreSQL，现有 `app.core.database` 接口已做了一层抽象，替换时只需改实现层。

## 6. 评测框架：为什么用 LLM-as-Judge 而不是人工标注

### 上下文

27 道测试用例，每次变更都需要验证 Agent 行为正确性。如果靠人工逐条看回复，一次评测要 30+ 分钟，不可能持续集成。

### 决策

**三段式自动评分：**

1. **硬评分（程序逻辑）**：工具调用召回率、升等标记、禁止操作触发。这些不需要 LLM，规则明确。
2. **LLM-as-Judge（内容评分）**：用 `qwen-max` 评估回复对标准答案信息点的覆盖度。**不做精确匹配**（因为 LLM 回复措辞每次可能不同），而是问 LLM"这个回复是否覆盖了以下信息点"。
3. **综合加权**：不同场景权重不同（正常场景 vs 升等中断场景）。

### 为什么可信

- 硬评分是确定性的，不依赖 LLM
- 内容评分只需判断"信息点是否覆盖"，不要求 LLM Judge 做主观判断，任务简单
- 升等中断场景下内容评分无意义（因为回复是审核员写的），权重自动调整

### 后续

可接入 cicd：每次 PR 自动跑 eval，评分低于阈值自动阻断。

## 7. 5 个工具的拆分粒度：为什么不合并成一个"万能工具"

### 上下文

Agent 需要能力：知识库查询、账号查询、创建工单、查工单进度、转人工。设计问题：拆成 5 个独立工具还是合并成 1 个万能工具让 LLM 自己决定参数？

### 决策

**拆成 5 个独立工具。** 理由：

- **工具选择也是评测指标**：如果一个 case 预期调用 `lookup_account` 但 LLM 调了 `create_ticket`，说明 LLM 理解错了意图，这是重要信号。合并成一个工具就丢失了这个信号。
- **权限隔离**：未来不同工具有不同权限（客服可以创建工单，但知识库查询对所有角色开放）
- **参数校验简单**：每个工具的参数是固定的，不需要 LLM 自行判断"这次调用需要用哪个参数组合"

### trade-off

Tool calling 的 token 消耗会增加（每个工具的 description 都要传给 LLM），5 个工具在合理范围内。

## 8. 配置管理：pydantic-settings + .env + 分层覆盖

### 上下文

配置项涉及多个 LLM Key、数据库连接、服务端口、特性开关（HIL）。需要一套清晰的配置管理策略。

### 决策

**三层覆盖（高优先级覆盖低优先级）：**

1. **环境变量**（最高优先级）：Docker 部署时通过 `environment` 注入
2. **`.env` 文件**：本地开发
3. **代码默认值**：兜底

用 `pydantic-settings` 实现，`Settings` 类集中管理所有配置项，类型校验 + 自动补全新开箱即用。

### 为什么不用 YAML/JSON 配置文件

- 敏感信息（API Key）不应进代码库
- 环境变量是 Docker 十二要素应用的标准做法
- pydantic-settings 自动读取 `.env`，不需要手写配置加载逻辑
