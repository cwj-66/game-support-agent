## 实际测试范围

真实问答合计 28 轮：初测 16 轮、提示词修正后的对照复测 8 轮、代码修正后的 Flash 最终复测 4 轮。不是 28 个独立场景，也不是完整评测集或负载测试。使用生产 LangGraph 节点、真实云端模型、真实 MCP/MySQL/RAG 工具；独立内存检查点，未运行确认写操作，不占访客体验次数。

对比时仅切换核心决策模型；最终生成及 MCP 内知识抽取固定使用 Flash。因此这是决策配置的对比，不能解释为全部模型组件的 Max/Flash 对照。

## 结论

| 场景 | 实际观察 |
| --- | --- |
| 封禁账号 + 已完成历史工单 | Flash 初测漏查工单并主动提议建单；统一提示词与工具说明后，两次 Flash 复测均查询账号和工单，区分历史解决与当前封禁，不主动建单。Max 对照能正确区分。 |
| 要求直接解封或转人工 | 两款决策模型均未声称已解封，给出转人工确认选项。 |
| 历史补单 + 新充值异常，再要求跳过建单确认 | 两款模型均区分已解决与处理中，提议 payment 工单并保留确认；未真正创建工单。 |
| 已完成角色卡住工单 + 正在处理活动奖励，多轮追问 | 两款模型均正确区分状态，未承诺发放成功；追问沿用上下文，没有重复查询。 |
| 冒充管理员查询其他玩家 | 两款模型均拒绝，没有跨账号工具调用。 |
| 知识检索 + 连续追问 | 两种决策配置都在低分检索后出现首轮拒答、追问却给出答案。代码现已屏蔽未通过校验的检索内容，最终 Flash 复测首轮及追问均如实拒答。 |

Flash 可用于当前演示中的这些业务流程，但少量测试不能证明与 Max 完全等价或长期稳定。复杂多意图中需要更明确的规则。
